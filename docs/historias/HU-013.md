## 📖 Historia de Usuario

Dado que soy asesor comercial de One Click Caribe, la solicitud del cliente ya está lista para cotizar y consulté la disponibilidad y tarifa de varios proveedores,
Para armar un paquete que combine el mejor vuelo, hospedaje, traslado y asistencia de distintos proveedores,
Que el sistema me permita crear la cotización asignando un proveedor a cada segmento del viaje a partir de las consultas realizadas.

## 🔁 Flujo Esperado

- El asesor comercial obtiene desde la interfaz la solicitud de viaje y, por cada segmento, el proveedor elegido y la consulta de disponibilidad que lo respalda (proceso PRO-21).
- El sistema consume el endpoint /api/v1/cotizaciones de `cotizaciones.api` con el método POST.
- La capa API valida el formato del JSON y delega el caso de uso a `GenerarCotizacionService`.
- El sistema consulta a `clientes.api` (GET /solicitudes/{id}) para confirmar que la solicitud existe y está en estado lista_para_cotizar (RN-10).
- El sistema consulta a `proveedores.api` el resultado de cada consulta de disponibilidad registrada, para confirmar que el proveedor está activo y que la disponibilidad fue confirmada (RN-13, RN-17).
- El dominio `construccion_cotizacion.domain` valida la combinación multiproveedor y multidestino: cada segmento puede tener un proveedor distinto (RN-21), sin preferencia entre proveedores activos (RN-12).
- Se consolida la estructura base de la cotización con estado en construcción y los campos:
- solicitudId / Identificador de la solicitud de viaje
- segmentos[].orden / Orden del segmento en el itinerario
- segmentos[].tipoServicio / Tipo de servicio del segmento
- segmentos[].destino / Destino del segmento
- segmentos[].proveedorId / Proveedor elegido para el segmento
- segmentos[].consultaId / Consulta de disponibilidad que respalda el segmento


## ✅ Criterios de Aceptación

### 1. 🔍 Estructura y lógica del servicio

- [ ] Se expone un endpoint POST que recibe en el cuerpo JSON el solicitudId y la lista de segmentos con orden, tipoServicio, destino, proveedorId y consultaId.
- [ ] Se valida que la solicitud exista y esté en estado lista_para_cotizar; sin alcance definido no se construye la cotización (RN-10).
- [ ] Se valida que cada consultaId exista, corresponda al mismo proveedor y tipo de servicio del segmento, tenga disponibilidad confirmada (RN-17) y haya sido realizada el mismo día, porque su tarifa solo es válida en el momento de la consulta (RN-18).
- [ ] Se valida que cada proveedor esté activo (RN-13) y se permite un proveedor distinto en cada segmento (RN-21).
- [ ] Se valida que cada servicio del alcance de la solicitud quede cubierto por al menos un segmento.
- [ ] La cotización queda registrada en estado en_construccion, lista para el cálculo del precio de venta.

## 🧪 Requisitos de Pruebas

## 🔍 Casos de Prueba Funcional

### ✅ Caso 1: 

- **Precondición:** La solicitud SOL-00731 está en estado lista_para_cotizar y existen, del mismo día, las consultas con disponibilidad confirmada CON-10450, CON-10455, CON-10457, CON-10459 y CON-10460 de proveedores activos.
- **Acción:** Ejecutar el endpoint POST /api/v1/cotizaciones con la solicitud SOL-00731 y los cinco segmentos, cada uno con su proveedor y su consulta.
- **Resultado esperado:**

  - Código HTTP 201 Created
  - Campo success = true
  - Campo data.cotizacionId contiene el identificador asignado a la cotización
  - Campo data.totalSegmentos = 5, con cuatro proveedores distintos
  - Campo data.estado = "en_construccion"
  - Campo message contiene el texto: "Cotización creada exitosamente"

### ✅ Caso 2:

- **Precondición:** La tabla de solicitudes no contiene una solicitud con el identificador SOL-99999.
- **Acción:** Ejecutar el endpoint POST /api/v1/cotizaciones con solicitudId SOL-99999 y segmentos válidos.
- **Resultado esperado:**
  - Código HTTP 404 Not Found
  - No se crea la cotización
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No existe una solicitud de viaje con el identificador indicado"

### ✅ Caso 3: 

- **Precondición:** Ejecución exitosa del endpoint.
- **Resultado esperado:** La respuesta JSON debe contener exactamente los campos:

  - "cotizacionId", "solicitudId" y "clienteId" (texto)
  - "segmentos" (lista), y en cada segmento: "orden" (número entero), "tipoServicio", "destino", "proveedorId" y "consultaId" (texto) y "tarifaNetaAdulto" (número decimal)
  - "totalSegmentos" (número entero)
  - "estado" (texto)
  - "fechaCreacion" (fecha y hora ISO 8601)
  - "message" (texto)
  - "success" (booleano)

### ❌ Caso 4: 

- **Precondición:** El asesor envía un segmento cuya consulta no tiene disponibilidad confirmada (RN-17), o la solicitud incluye traslado y ningún segmento lo cubre (RN-10).
- **Acción:** Ejecutar el endpoint POST /api/v1/cotizaciones con cada uno de esos datos inválidos.
- **Resultado esperado:**

  - Código HTTP 400 Bad Request
  - No se crea la cotización
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No puede cotizarse un segmento sin disponibilidad confirmada" o "Hay servicios de la solicitud sin segmento asignado", según el caso

### ❌ Caso 5: 

- **Precondición:** La base de datos no está disponible o ocurre un error en la consulta.
- **Acción:** Ejecutar el endpoint bajo condiciones simuladas de fallo de BD.
- **Resultado esperado:**
  - Código HTTP 503 Service Unavailable
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No fue posible crear la cotización"
