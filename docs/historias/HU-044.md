## 📖 Historia de Usuario

Dado que soy asesor comercial de One Click Caribe y la orden de venta incluye un viaje internacional,
Para no emitir reservas para pasajeros que no podrían viajar por pasaporte vencido, falta de visa o requisitos de su nacionalidad,
Que el sistema me permita validar los requisitos documentales de cada pasajero y obtener un dictamen apto o no apto que bloquee la emisión cuando no se cumplen.

## 🔁 Flujo Esperado

- El asesor comercial obtiene desde la interfaz la orden de venta cuyos pasajeros va a validar (procesos PRO-71, PRO-72 y PRO-73).
- El sistema consume el endpoint /api/v1/reservas/validaciones-documentales de `reservas.api` con el método POST.
- La capa API valida el formato del JSON y delega el caso de uso a `ValidarRequisitosDocumentalesService`.
- El sistema consulta a `ventas.api` los destinos y la fecha de regreso del viaje, y a `clientes.api` (GET /clientes/{id}/pasajeros) la nacionalidad y el pasaporte de cada pasajero.
- El dominio `validacion_requisitos_documentales.domain` valida, si el destino es internacional, que el pasaporte de cada pasajero esté vigente para las fechas del viaje (RN-71).
- El dominio valida la visa únicamente cuando algún destino es Estados Unidos (RN-72), y determina los requisitos migratorios adicionales según la nacionalidad registrada de cada pasajero (RN-73).
- Si un pasaporte está vencido y el cliente no ha registrado el compromiso de renovarlo, el pasajero queda no apto y se bloquea la emisión de la reserva de la orden (proceso PRO-75, RN-74, RN-75).
- Se registra el dictamen de la orden en la base de datos `bd_reservas` con los campos:
- pasajeros[].pasaporteVigente / Resultado de la vigencia del pasaporte
- pasajeros[].visaRequerida y visaValida / Resultado de la validación de visa
- pasajeros[].requisitosNacionalidad / Requisitos adicionales por nacionalidad
- pasajeros[].dictamen / apto o no_apto
- emisionBloqueada / Indica si la emisión de la orden queda bloqueada


## ✅ Criterios de Aceptación

### 1. 🔍 Estructura y lógica del servicio

- [ ] Se expone un endpoint POST que recibe en el cuerpo JSON el ventaId de la orden a validar.
- [ ] Se valida que la orden exista; si no existe, se retorna código HTTP 404.
- [ ] Si la orden tiene algún destino internacional, se valida que el pasaporte de cada pasajero esté vigente hasta la fecha de regreso del viaje (RN-71); en viajes nacionales la validación no aplica.
- [ ] La visa solo se exige cuando algún destino de la orden es Estados Unidos (RN-72).
- [ ] Los requisitos adicionales se determinan según la nacionalidad registrada del pasajero, no solo según el destino (RN-73).
- [ ] Un pasajero con pasaporte vencido solo queda apto si el cliente registró el compromiso de renovarlo antes del viaje (RN-74); de lo contrario queda no_apto, la emisión de la orden se bloquea y, si el cliente no asume el compromiso, se inicia el reembolso del dinero pagado (RN-75).

## 🧪 Requisitos de Pruebas

## 🔍 Casos de Prueba Funcional

### ✅ Caso 1: 

- **Precondición:** La orden VEN-01532 tiene destinos en México con regreso el 2026-12-20, y sus dos pasajeros de nacionalidad CO tienen pasaportes que vencen el 2030-08-01 y el 2028-02-15.
- **Acción:** Ejecutar el endpoint POST /api/v1/reservas/validaciones-documentales con ventaId VEN-01532.
- **Resultado esperado:**

  - Código HTTP 200 OK
  - Cada pasajero tiene pasaporteVigente = true, visaRequerida = false y dictamen = "apto"
  - Campo data.emisionBloqueada = false
  - Campo success = true
  - Campo message contiene el texto: "Validación documental exitosa: todos los pasajeros cumplen los requisitos"

### ✅ Caso 2:

- **Precondición:** La orden VEN-01547 es un viaje internacional y su pasajero PAS-00440 tiene el pasaporte vencido, sin compromiso de renovación registrado.
- **Acción:** Ejecutar el endpoint con POST /api/v1/reservas/validaciones-documentales y ventaId VEN-01547.
- **Resultado esperado:**
  - Código HTTP 200 OK
  - Campo pasaporteVigente = false y campo dictamen = "no_apto" para el pasajero PAS-00440
  - Campo emisionBloqueada = true
  - Campo accionRequerida = "registrar_compromiso_o_reembolsar"
  - Campo message contiene el texto: "Hay pasajeros que no cumplen los requisitos documentales. La emisión de la reserva queda bloqueada"

### ✅ Caso 3: 

- **Precondición:** Ejecución exitosa del endpoint.
- **Resultado esperado:** La respuesta JSON debe contener exactamente los campos:

  - "ventaId" (texto)
  - "destinoInternacional" y "emisionBloqueada" (booleano)
  - "fechaRegreso" (fecha YYYY-MM-DD)
  - "pasajeros" (lista), y en cada pasajero: "pasajeroId", "nacionalidad" y "dictamen" (texto), "pasaporteVigente" y "visaRequerida" (booleano), "visaValida" (booleano, o null si no aplica) y "requisitosNacionalidad" (lista de texto)
  - "fechaValidacion" (fecha y hora ISO 8601)
  - "message" (texto)
  - "success" (booleano)

### ❌ Caso 4: 

- **Precondición:** El asesor envía el parámetro ventaId con formato incorrecto (por ejemplo, "1532").
- **Acción:** Ejecutar el endpoint POST /api/v1/reservas/validaciones-documentales con ventaId 1532.
- **Resultado esperado:**

  - Código HTTP 400 Bad Request
  - No se registra ningún dictamen
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "Identificador de venta no válido. Debe tener el formato VEN-NNNNN"

### ❌ Caso 5: 

- **Precondición:** La base de datos no está disponible o ocurre un error en la consulta.
- **Acción:** Ejecutar el endpoint bajo condiciones simuladas de fallo de BD.
- **Resultado esperado:**
  - Código HTTP 503 Service Unavailable
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No fue posible validar los requisitos documentales"
