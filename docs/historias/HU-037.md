## 📖 Historia de Usuario

Dado que soy asesor comercial de One Click Caribe y Tesorería ya registró el pago al proveedor de uno o varios segmentos de la orden de venta,
Para ejecutar lo que el cliente compró y asegurar cada servicio del viaje con su proveedor,
Que el sistema me permita solicitar la reserva de cada segmento pagado en la plataforma del proveedor correspondiente.

## 🔁 Flujo Esperado

- El asesor comercial obtiene desde la interfaz la orden de venta y los segmentos que va a reservar (proceso PRO-61).
- El sistema consume el endpoint /api/v1/reservas de `reservas.api` con el método POST.
- La capa API valida el formato del JSON y delega el caso de uso a `SolicitarReservaService`.
- El backend consulta la base de datos `bd_reservas` filtrando por ventaId para confirmar que Tesorería habilitó la reserva de cada segmento al registrar el pago al proveedor.
- El dominio `emision_confirmacion_reserva.domain` ejecuta `Reserva.puedeConfirmarse()`: un segmento solo se reserva si el pago al proveedor correspondiente ya está registrado en Tesorería (RN-61).
- El dominio verifica que ningún pasajero de la orden tenga la emisión bloqueada por incumplimiento documental (RN-75).
- El sistema ejecuta la solicitud de reserva en la plataforma del proveedor a través de `proveedores.api` (POST /proveedores/reservas), con los datos del servicio y de los pasajeros.
- Se registra cada solicitud en estado solicitada, a la espera del código de confirmación del proveedor, con los campos:
- reservaId / Identificador de la solicitud de reserva
- ventaId / Orden de venta
- orden / Segmento de la orden reservado
- proveedorId / Proveedor al que se solicitó
- tipoServicio / Servicio reservado
- fechaSolicitud / Momento de la solicitud


## ✅ Criterios de Aceptación

### 1. 🔍 Estructura y lógica del servicio

- [ ] Se expone un endpoint POST que recibe en el cuerpo JSON el ventaId y la lista de segmentos a reservar.
- [ ] Se valida que la orden de venta exista y que cada segmento enviado pertenezca a ella.
- [ ] Se valida que cada segmento tenga el pago al proveedor registrado en Tesorería; sin ese pago la reserva no se solicita (RN-61).
- [ ] Se valida que ningún pasajero de la orden tenga la emisión bloqueada por incumplimiento documental (RN-75).
- [ ] Se valida que el segmento no tenga ya una reserva solicitada o confirmada, para no duplicar la reserva con el proveedor.
- [ ] Cada segmento solicitado queda en estado solicitada, con su propio registro, aunque varios segmentos sean del mismo proveedor.


### 2. 📆 Estructura de la información

- [ ] Se responde con la siguiente estructura en JSON:

```json

  "data": {

    "reservas": [
```

## 🧪 Requisitos de Pruebas

## 🔍 Casos de Prueba Funcional

### ✅ Caso 1: 

- **Precondición:** La orden VEN-01532 tiene registrados en Tesorería el pago al proveedor PRV-0021 por los segmentos 3 y 4, y ningún pasajero tiene bloqueo documental.
- **Acción:** Ejecutar el endpoint POST /api/v1/reservas con ventaId VEN-01532 y los segmentos 3 y 4.
- **Resultado esperado:**

  - Código HTTP 201 Created
  - Campo data.totalSolicitadas = 2
  - Cada segmento tiene su propio reservaId y estado = "solicitada"
  - Campo success = true
  - Campo message contiene el texto: "Solicitud de reserva registrada exitosamente"

### ✅ Caso 2:

- **Precondición:** La tabla de órdenes de venta no contiene una orden con el identificador VEN-99999.
- **Acción:** Ejecutar el endpoint POST /api/v1/reservas con ventaId VEN-99999 y el segmento 1.
- **Resultado esperado:**
  - Código HTTP 404 Not Found
  - No se solicita ninguna reserva al proveedor
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No existe una orden de venta con el identificador indicado"

### ✅ Caso 3: 

- **Precondición:** Ejecución exitosa del endpoint.
- **Resultado esperado:** La respuesta JSON debe contener exactamente los campos:

  - "ventaId" (texto)
  - "reservas" (lista), y en cada reserva: "reservaId", "proveedorId", "tipoServicio" y "estado" (texto) y "orden" (número entero)
  - "totalSolicitadas" (número entero)
  - "fechaSolicitud" (fecha y hora ISO 8601)
  - "message" (texto)
  - "success" (booleano)

### ❌ Caso 4: 

- **Precondición:** El asesor intenta reservar el segmento 1 de la orden VEN-01532, cuyo pago al proveedor aún no está registrado en Tesorería (RN-61), o un segmento de una orden con un pasajero bloqueado por incumplimiento documental (RN-75).
- **Acción:** Ejecutar el endpoint POST /api/v1/reservas con cada uno de esos segmentos.
- **Resultado esperado:**

  - Código HTTP 400 Bad Request
  - No se solicita la reserva al proveedor
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No puede reservarse un segmento sin el pago al proveedor registrado" o "La emisión está bloqueada por incumplimiento documental de un pasajero", según el caso

### ❌ Caso 5: 

- **Precondición:** La base de datos o la plataforma del proveedor no está disponible.
- **Acción:** Ejecutar el endpoint bajo condiciones simuladas de fallo de BD o de la plataforma del proveedor.
- **Resultado esperado:**
  - Código HTTP 503 Service Unavailable
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No fue posible solicitar la reserva al proveedor"
