## 📖 Historia de Usuario

Dado que soy asesor comercial de One Click Caribe y ya registré el itinerario base de la solicitud de viaje del cliente,
Para definir qué se va a cotizar y para cuántas personas, distinguiendo adultos y menores con su edad exacta,
Que el sistema me permita registrar la composición del grupo de viaje, los tipos de servicio que requiere el cliente y el tipo de acomodación cuando incluye hospedaje.

## 🔁 Flujo Esperado

- El asesor comercial obtiene desde la interfaz el identificador de la solicitud, el número de adultos, la edad de cada menor y los servicios requeridos (procesos PRO-09 y PRO-10).
- El sistema consume el endpoint /api/v1/solicitudes/{solicitudId}/alcance de `clientes.api` con el método PUT.
- La capa API valida el formato del JSON y delega el caso de uso a `DefinirAlcanceSolicitudService`.
- El backend consulta la base de datos `bd_clientes_solicitudes` filtrando por solicitudId para confirmar que la solicitud existe.
- El dominio `registro_parametros_viaje.domain` exige la edad exacta de cada menor, porque de ella depende la tarifa infantil aplicada en Cotizaciones (RN-07).
- El dominio exige que el alcance del servicio quede explícito antes de continuar (RN-10) y, si incluye hospedaje, que se registre el tipo de acomodación (RN-09).
- Se registra el alcance de la solicitud y su estado cambia a lista para cotizar, con los campos:
- composicion.adultos / Número de adultos
- composicion.menores[].edad / Edad exacta de cada menor
- servicios / Tipos de servicio requeridos (tiquete_aereo, hospedaje, traslado, tour, crucero, alquiler_vehiculo, asistencia_medica)
- tipoAcomodacion / Tipo de acomodación (individual, doble, triple o cuadruple), obligatorio cuando se incluye hospedaje


## ✅ Criterios de Aceptación

### 1. 🔍 Estructura y lógica del servicio

- [ ] Se expone un endpoint PUT con el parámetro solicitudId en la ruta y la composición, los servicios y el tipo de acomodación en el cuerpo JSON.
- [ ] Se valida que el solicitudId recibido tenga un registro en la tabla de solicitudes.
- [ ] Se valida que haya al menos un adulto y que cada menor tenga su edad exacta registrada, entre 0 y 17 años (RN-07).
- [ ] Se valida que la lista de servicios tenga al menos un tipo de servicio del catálogo; sin alcance explícito la solicitud no puede pasar a Cotizaciones (RN-10).
- [ ] Se valida que tipoAcomodacion esté informado cuando los servicios incluyen hospedaje (RN-09).
- [ ] Al registrarse el alcance, la solicitud cambia de estado pendiente_alcance a lista_para_cotizar.

## 🧪 Requisitos de Pruebas

## 🔍 Casos de Prueba Funcional

### ✅ Caso 1: 

- **Precondición:** La tabla de solicitudes contiene la solicitud SOL-00731 en estado pendiente_alcance.
- **Acción:** Ejecutar el endpoint PUT /api/v1/solicitudes/SOL-00731/alcance con 2 adultos, sin menores, los servicios tiquete_aereo, hospedaje, traslado y asistencia_medica, y acomodación doble.
- **Resultado esperado:**

  - Código HTTP 200 OK
  - Campo success = true
  - Campo data.composicion.totalPasajeros = 2
  - Campo data.estado = "lista_para_cotizar"
  - Campo message contiene el texto: "Alcance de la solicitud registrado exitosamente"

### ✅ Caso 2:

- **Precondición:** La tabla de solicitudes no contiene una solicitud con el identificador SOL-99999.
- **Acción:** Ejecutar el endpoint PUT /api/v1/solicitudes/SOL-99999/alcance con un alcance válido.
- **Resultado esperado:**
  - Código HTTP 404 Not Found
  - No se registra ningún alcance
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No existe una solicitud de viaje con el identificador indicado"

### ✅ Caso 3: 

- **Precondición:** Ejecución exitosa del endpoint.
- **Resultado esperado:** La respuesta JSON debe contener exactamente los campos:

  - "solicitudId" (texto)
  - "composicion" (objeto con "adultos" y "totalPasajeros" de tipo número entero, y "menores" como lista de objetos con "edad" de tipo número entero)
  - "servicios" (lista de texto)
  - "tipoAcomodacion" (texto)
  - "estado" (texto)
  - "fechaActualizacion" (fecha y hora ISO 8601)
  - "message" (texto)
  - "success" (booleano)

### ❌ Caso 4: 

- **Precondición:** El asesor envía un menor sin su edad registrada (RN-07), o incluye hospedaje en los servicios sin informar tipoAcomodacion (RN-09).
- **Acción:** Ejecutar el endpoint PUT /api/v1/solicitudes/SOL-00731/alcance con cada uno de esos datos inválidos.
- **Resultado esperado:**

  - Código HTTP 400 Bad Request
  - No se registra el alcance y la solicitud sigue en estado pendiente_alcance
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "La edad de cada menor es obligatoria" o "El tipo de acomodación es obligatorio cuando se incluye hospedaje", según el caso

### ❌ Caso 5: 

- **Precondición:** La base de datos no está disponible o ocurre un error en la consulta.
- **Acción:** Ejecutar el endpoint bajo condiciones simuladas de fallo de BD.
- **Resultado esperado:**
  - Código HTTP 503 Service Unavailable
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No fue posible registrar el alcance de la solicitud"
