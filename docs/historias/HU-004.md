## 📖 Historia de Usuario

Dado que soy asesor comercial de One Click Caribe y el cliente titular ya está registrado, pero quien paga no siempre es el único que viaja,
Para cotizar, reservar y validar los documentos de cada persona que viaja, aunque pague un solo titular,
Que el sistema me permita asociar al cliente titular los pasajeros del viaje con su documento, fecha de nacimiento, nacionalidad y datos de pasaporte.

## 🔁 Flujo Esperado

- El asesor comercial obtiene desde la interfaz el identificador del cliente titular y la lista de pasajeros que viajan (proceso PRO-05).
- El sistema consume el endpoint /api/v1/clientes/{clienteId}/pasajeros de `clientes.api` con el método POST.
- La capa API valida el formato del JSON y delega el caso de uso a `AsociarPasajerosService`.
- El backend consulta la base de datos `bd_clientes_solicitudes` filtrando por clienteId para confirmar que el cliente titular existe.
- El dominio `registro_cliente_pasajeros.domain` valida si el cliente titular también figura como pasajero del viaje (RN-03).
- Se registra la relación titular-pasajeros con los campos:
- nombre / Nombre completo del pasajero
- documento / Documento de identidad
- fechaNacimiento / Fecha de nacimiento (de ella se calcula la edad que usa la tarifa por adulto o menor)
- nacionalidad / Nacionalidad (código ISO de 2 letras, base de los requisitos migratorios)
- esTitular / Indica si el pasajero es el mismo cliente titular
- numeroPasaporte / Número de pasaporte (cuando el viaje es internacional)
- vencimientoPasaporte / Fecha de vencimiento del pasaporte


## ✅ Criterios de Aceptación

### 1. 🔍 Estructura y lógica del servicio

- [ ] Se expone un endpoint POST con el parámetro clienteId en la ruta y la lista de pasajeros en el cuerpo JSON.
- [ ] Se valida que el clienteId recibido tenga un registro en la tabla de clientes.
- [ ] Se valida que cada pasajero tenga nombre, documento, fechaNacimiento y nacionalidad informados.
- [ ] Se permite que el cliente titular sea también uno de los pasajeros (RN-03); en ese caso, solo un pasajero puede tener esTitular = true y su documento debe coincidir con el del cliente titular.
- [ ] Se valida que no se repita el mismo documento entre los pasajeros asociados a un mismo cliente titular.
- [ ] Si se informa numeroPasaporte, también debe informarse vencimientoPasaporte, porque ambos se usan en la validación documental del viaje.

## 🧪 Requisitos de Pruebas

## 🔍 Casos de Prueba Funcional

### ✅ Caso 1: 

- **Precondición:** La tabla de clientes contiene el cliente titular CLI-00188 con documento 1098765432.
- **Acción:** Ejecutar el endpoint POST /api/v1/clientes/CLI-00188/pasajeros con dos pasajeros: la titular (esTitular = true, documento 1098765432) y su acompañante (esTitular = false).
- **Resultado esperado:**

  - Código HTTP 201 Created
  - Campo success = true
  - Campo data.totalPasajeros = 2
  - Cada pasajero tiene un pasajeroId asignado y su edad calculada a partir de fechaNacimiento
  - Campo message contiene el texto: "Pasajeros asociados exitosamente"

### ✅ Caso 2:

- **Precondición:** La tabla de clientes no contiene un cliente titular con el identificador CLI-99999.
- **Acción:** Ejecutar el endpoint POST /api/v1/clientes/CLI-99999/pasajeros con una lista válida de pasajeros.
- **Resultado esperado:**
  - Código HTTP 404 Not Found
  - No se registra ningún pasajero
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No existe un cliente titular con el identificador indicado"

### ✅ Caso 3: 

- **Precondición:** Ejecución exitosa del endpoint.
- **Resultado esperado:** La respuesta JSON debe contener exactamente los campos:

  - "clienteId" (texto)
  - "pasajeros" (lista), y en cada pasajero: "pasajeroId", "nombre", "documento", "nacionalidad", "numeroPasaporte" (texto), "fechaNacimiento" y "vencimientoPasaporte" (fecha YYYY-MM-DD), "edad" (número entero) y "esTitular" (booleano)
  - "totalPasajeros" (número entero)
  - "message" (texto)
  - "success" (booleano)

### ❌ Caso 4: 

- **Precondición:** El asesor envía un pasajero con fechaNacimiento en formato incorrecto (por ejemplo, "12-05-1994"), o con dos pasajeros marcados como esTitular = true.
- **Acción:** Ejecutar el endpoint POST /api/v1/clientes/CLI-00188/pasajeros con cada uno de esos datos inválidos.
- **Resultado esperado:**

  - Código HTTP 400 Bad Request
  - No se registra ningún pasajero de la lista
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "Formato de fecha no válido. Debe ser YYYY-MM-DD" o "Solo un pasajero puede ser el cliente titular", según el caso

### ❌ Caso 5: 

- **Precondición:** La base de datos no está disponible o ocurre un error en la consulta.
- **Acción:** Ejecutar el endpoint bajo condiciones simuladas de fallo de BD.
- **Resultado esperado:**
  - Código HTTP 503 Service Unavailable
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No fue posible asociar los pasajeros"
