## 📖 Historia de Usuario

Dado que soy asesor comercial de One Click Caribe y el cliente ya recibió la cotización y me comunica su decisión,
Para saber qué cotizaciones se convierten en venta y conservar en el historial el motivo de las que se rechazan,
Que el sistema me permita registrar la respuesta del cliente a la cotización: aceptada, rechazada o con ajuste solicitado.

## 🔁 Flujo Esperado

- El asesor comercial obtiene desde la interfaz la cotización enviada y la respuesta del cliente, con el motivo cuando la rechaza o pide un ajuste (proceso PRO-28).
- El sistema consume el endpoint /api/v1/cotizaciones/{cotizacionId}/respuesta de `cotizaciones.api` con el método POST.
- La capa API valida el formato del JSON y delega el caso de uso a `RegistrarRespuestaClienteService`.
- El backend consulta la base de datos `bd_cotizaciones` filtrando por cotizacionId para confirmar que la cotización existe y está en estado enviada.
- El dominio `vigencia_respuesta_cotizacion.domain` ejecuta `Cotizacion.estaVigente()`: una cotización vencida no puede aceptarse (RN-28).
- Si la respuesta es rechazo, el dominio exige el motivo y lo conserva en el historial, aun si el cliente solicita después una nueva cotización (RN-30).
- Si la respuesta es aceptación, se informa que el precio solo queda garantizado si el cliente paga, total o parcialmente, antes del cierre del mismo día (RN-27).
- Se actualiza el estado de la cotización y se conserva el registro con los campos:
- respuesta / aceptada, rechazada o ajuste_solicitado
- motivo / Motivo del rechazo o detalle del ajuste solicitado
- fechaHoraRespuesta / Momento en que se registró la respuesta
- pagoRequeridoAntesDe / Límite para pagar y garantizar el precio, cuando es aceptada


## ✅ Criterios de Aceptación

### 1. 🔍 Estructura y lógica del servicio

- [ ] Se expone un endpoint POST con el parámetro cotizacionId en la ruta y la respuesta y el motivo en el cuerpo JSON.
- [ ] Se valida que la cotización exista y esté en estado enviada.
- [ ] Se valida que la cotización siga vigente; una cotización vencida no puede aceptarse y debe generarse una nueva (RN-28).
- [ ] Se valida que respuesta sea aceptada, rechazada o ajuste_solicitado, y que motivo esté informado cuando es rechazada o ajuste_solicitado (RN-30).
- [ ] El motivo de rechazo se conserva en el historial de la cotización y no se elimina aunque el cliente pida una nueva (RN-30).
- [ ] Si es aceptada, la respuesta indica que el precio solo se garantiza con un pago total o parcial antes del cierre del día de emisión (RN-27).


### 2. 📆 Estructura de la información

- [ ] Se responde con la siguiente estructura en JSON:

## 🧪 Requisitos de Pruebas

## 🔍 Casos de Prueba Funcional

### ✅ Caso 1: 

- **Precondición:** La cotización COT-07421 está en estado enviada y vigente hasta las 23:59:59 del día de su emisión.
- **Acción:** Ejecutar el endpoint POST /api/v1/cotizaciones/COT-07421/respuesta con respuesta aceptada.
- **Resultado esperado:**

  - Código HTTP 200 OK
  - Campo data.estado = "aceptada"
  - Campo data.pagoRequeridoAntesDe coincide con el límite de vigencia de la cotización
  - Campo success = true
  - Campo message contiene el texto: "Respuesta del cliente registrada exitosamente"

### ✅ Caso 2:

- **Precondición:** La tabla de cotizaciones no contiene una cotización con el identificador COT-99999.
- **Acción:** Ejecutar el endpoint POST /api/v1/cotizaciones/COT-99999/respuesta con respuesta rechazada y un motivo.
- **Resultado esperado:**
  - Código HTTP 404 Not Found
  - No se registra ninguna respuesta
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No existe una cotización con el identificador indicado"

### ✅ Caso 3: 

- **Precondición:** Ejecución exitosa del endpoint.
- **Resultado esperado:** La respuesta JSON debe contener exactamente los campos:

  - "cotizacionId", "clienteId", "respuesta" y "estado" (texto)
  - "motivo" (texto, o null cuando la respuesta es aceptada)
  - "fechaHoraRespuesta" (fecha y hora ISO 8601)
  - "pagoRequeridoAntesDe" (fecha y hora ISO 8601, o null cuando no es aceptada)
  - "message" (texto)
  - "success" (booleano)

### ❌ Caso 4: 

- **Precondición:** El asesor registra un rechazo sin motivo (RN-30), o intenta registrar la aceptación de la cotización COT-07415, que está vencida (RN-28).
- **Acción:** Ejecutar el endpoint POST /api/v1/cotizaciones/{cotizacionId}/respuesta con cada uno de esos datos inválidos.
- **Resultado esperado:**

  - Código HTTP 400 Bad Request
  - No se modifica el estado de la cotización
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "El motivo del rechazo es obligatorio" o "La cotización está vencida. Debe generarse una nueva con tarifas actualizadas", según el caso

### ❌ Caso 5: 

- **Precondición:** La base de datos no está disponible o ocurre un error en la consulta.
- **Acción:** Ejecutar el endpoint bajo condiciones simuladas de fallo de BD.
- **Resultado esperado:**
  - Código HTTP 503 Service Unavailable
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No fue posible registrar la respuesta del cliente"
