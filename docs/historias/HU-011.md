## 📖 Historia de Usuario

Dado que soy asesor comercial de One Click Caribe y la agencia no tiene tarifas fijas pactadas con ningún proveedor,
Para cotizar con el precio real del momento y no con un valor supuesto,
Que el sistema me permita consultar en tiempo real la disponibilidad y la tarifa vigente de un servicio con un proveedor, dejando registrado el resultado de la consulta.

## 🔁 Flujo Esperado

- El asesor comercial obtiene desde la interfaz el proveedor, el tipo de servicio, el destino, las fechas y el número de pasajeros de la solicitud (procesos PRO-16 y PRO-17).
- El sistema consume el endpoint /api/v1/proveedores/disponibilidad?proveedorId=PRV-XXXX&tipoServicio=...&destino=...&fechaInicio=YYYY-MM-DD&fechaFin=YYYY-MM-DD&adultos=N&menores=N.
- La capa API valida el formato de los parámetros y delega el caso de uso a `ConsultarDisponibilidadService` de `proveedores.api`.
- El backend consulta la base de datos `bd_proveedores` filtrando por proveedorId para confirmar que el proveedor existe y está activo (RN-13).
- El sistema consulta en tiempo real la plataforma del proveedor, sin recurrir a tarifas fijas ni pactadas de antemano (RN-16).
- El dominio `consulta_disponibilidad_tarifas.domain` marca el resultado con la fecha y hora de la consulta, porque solo es válido para ese momento (RN-18).
- Si hay disponibilidad, se registra temporalmente el resultado para uso de Cotizaciones (proceso PRO-19, RN-17), con los campos:
- disponible / Disponibilidad confirmada por el proveedor
- tarifaNetaAdulto / Tarifa neta del proveedor por pasajero adulto
- tarifaNetaMenor / Tarifa neta del proveedor por pasajero menor
- moneda / Moneda de la tarifa
- fechaHoraConsulta / Momento exacto de la consulta
- Si no hay cupo, se genera la alerta para que el asesor ajuste los parámetros de búsqueda (proceso PRO-20, RN-20).


## ✅ Criterios de Aceptación

### 1. 🔍 Estructura y lógica del servicio

- [ ] Se expone un endpoint GET con los parámetros proveedorId, tipoServicio, destino, fechaInicio, fechaFin, adultos y menores.
- [ ] Se valida que el proveedor exista y esté activo; un proveedor desactivado no puede usarse para nuevas cotizaciones (RN-13).
- [ ] Se valida que tipoServicio corresponda a uno de los servicios que ofrece el proveedor.
- [ ] La tarifa se obtiene en tiempo real de la plataforma del proveedor, nunca de un valor fijo almacenado (RN-16).
- [ ] Cada resultado queda registrado con su consultaId y su fecha y hora, y solo se pone a disposición de Cotizaciones cuando la disponibilidad está confirmada (RN-17, RN-18).
- [ ] Si el proveedor no reporta cupo, la respuesta indica al asesor que debe ajustar los parámetros de búsqueda (RN-20).

## 🧪 Requisitos de Pruebas

## 🔍 Casos de Prueba Funcional

### ✅ Caso 1: 

- **Precondición:** El proveedor PRV-0021 está activo, ofrece hospedaje y su plataforma reporta cupo en Cancún entre el 2026-12-15 y el 2026-12-20.
- **Acción:** Ejecutar el endpoint GET /api/v1/proveedores/disponibilidad?proveedorId=PRV-0021&tipoServicio=hospedaje&destino=Cancún&fechaInicio=2026-12-15&fechaFin=2026-12-20&adultos=2&menores=0.
- **Resultado esperado:**

  - Código HTTP 200 OK
  - Campo success = true y campo data.disponible = true
  - Campos data.tarifaNetaAdulto y data.tarifaNetaMenor contienen la tarifa reportada por el proveedor en ese momento
  - Campo data.fechaHoraConsulta contiene la fecha y hora de la consulta
  - Campo message contiene el texto: "Consulta de disponibilidad exitosa"

### ✅ Caso 2:

- **Precondición:** La plataforma del proveedor PRV-0021 no reporta cupo en Cancún para las fechas 2026-12-24 a 2026-12-31.
- **Acción:** Ejecutar el endpoint con GET /api/v1/proveedores/disponibilidad?proveedorId=PRV-0021&tipoServicio=hospedaje&destino=Cancún&fechaInicio=2026-12-24&fechaFin=2026-12-31&adultos=2&menores=0.
- **Resultado esperado:**
  - Código HTTP 200 OK
  - Campo disponible = false
  - Campo tarifaNetaAdulto = 0
  - Campo tarifaNetaMenor = 0
  - El resultado no queda disponible para Cotizaciones
  - Campo message contiene el texto: "El proveedor no reporta disponibilidad para los parámetros indicados. Ajuste la búsqueda"

### ✅ Caso 3: 

- **Precondición:** Ejecución exitosa del endpoint.
- **Resultado esperado:** La respuesta JSON debe contener exactamente los campos:

  - "consultaId", "proveedorId", "tipoServicio", "destino" y "moneda" (texto)
  - "fechaInicio" y "fechaFin" (fecha YYYY-MM-DD)
  - "adultos" y "menores" (número entero)
  - "disponible" (booleano)
  - "tarifaNetaAdulto" y "tarifaNetaMenor" (número decimal)
  - "fechaHoraConsulta" (fecha y hora ISO 8601)
  - "message" (texto)
  - "success" (booleano)

### ❌ Caso 4: 

- **Precondición:** El usuario envía el parámetro fechaInicio con formato incorrecto (por ejemplo, "15-12-2026").
- **Acción:** Ejecutar el endpoint con GET /api/v1/proveedores/disponibilidad?proveedorId=PRV-0021&tipoServicio=hospedaje&destino=Cancún&fechaInicio=15-12-2026&fechaFin=2026-12-20&adultos=2&menores=0.
- **Resultado esperado:**

  - Código HTTP 400 Bad Request
  - No se consulta la plataforma del proveedor
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "Formato de fecha no válido. Debe ser YYYY-MM-DD"

### ❌ Caso 5: 

- **Precondición:** La base de datos o la plataforma del proveedor no está disponible.
- **Acción:** Ejecutar el endpoint bajo condiciones simuladas de fallo de BD o de la plataforma del proveedor.
- **Resultado esperado:**
  - Código HTTP 503 Service Unavailable
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No fue posible consultar la disponibilidad del proveedor"
