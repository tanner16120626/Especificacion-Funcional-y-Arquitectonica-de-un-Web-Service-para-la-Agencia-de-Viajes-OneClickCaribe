## 📖 Historia de Usuario

Dado que soy asesor comercial de One Click Caribe y el cliente me entrega el soporte de un pago en efectivo o por transferencia,
Para dejar constancia de cada dinero recibido desde el momento en que el cliente lo reporta, asociado a su orden de venta,
Que el sistema me permita registrar el pago del cliente, sea por el valor total o como abono parcial, con su soporte.

## 🔁 Flujo Esperado

- El asesor comercial obtiene desde la interfaz la orden de venta, el monto, el medio de pago, el tipo de pago y el número del comprobante entregado por el cliente (procesos PRO-41 y PRO-43).
- El sistema consume el endpoint /api/v1/pagos/cliente de `pagos.api` con el método POST.
- La capa API valida el formato del JSON y delega el caso de uso a `RegistrarPagoClienteService`.
- El sistema consulta a `ventas.api` la orden de venta para confirmar que existe, su valor total y su modalidad de pago.
- El dominio `recaudo_verificacion_pago.domain` valida que el medio de pago sea efectivo o transferencia (RN-41) y que el pago quede asociado a una orden de venta específica, nunca como ingreso genérico (RN-44).
- Si el tipo de pago es abono, el dominio verifica que la orden permita pago parcial (proceso PRO-43).
- Se registra el pago en estado pendiente de verificación, porque el comprobante no es prueba suficiente hasta confirmar el ingreso real en la cuenta (RN-42), con los campos:
- ventaId / Orden de venta a la que se asocia el pago
- tipoPago / total o abono
- medioPago / efectivo o transferencia
- monto / Valor pagado
- numeroComprobante / Número del soporte entregado por el cliente
- fechaPago / Fecha en que el cliente realizó el pago


## ✅ Criterios de Aceptación

### 1. 🔍 Estructura y lógica del servicio

- [ ] Se expone un endpoint POST que recibe en el cuerpo JSON los campos ventaId, tipoPago, medioPago, monto, numeroComprobante y fechaPago.
- [ ] Se valida que la orden de venta exista; todo pago queda asociado a una orden específica (RN-44).
- [ ] Se valida que medioPago sea efectivo o transferencia; no se aceptan tarjeta ni financiación (RN-41).
- [ ] Se valida que un abono solo se registre si la orden tiene modalidad de pago parcial, y que un pago total sea igual al valor pendiente de la orden.
- [ ] Se valida que el monto sea mayor que cero y no supere el valor pendiente de la orden.
- [ ] El pago queda en estado pendiente_verificacion hasta que la administradora confirme el ingreso real en la cuenta (RN-42).

## 🧪 Requisitos de Pruebas

## 🔍 Casos de Prueba Funcional

### ✅ Caso 1: 

- **Precondición:** La orden de venta VEN-01532 existe, tiene modalidad de pago parcial y un valor total de 11038400.
- **Acción:** Ejecutar el endpoint POST /api/v1/pagos/cliente con ventaId VEN-01532, tipoPago abono, medioPago transferencia, monto 5000000 y numeroComprobante TRF-884213.
- **Resultado esperado:**

  - Código HTTP 201 Created
  - Campo data.pagoId contiene el identificador asignado al pago
  - Campo data.ventaId = "VEN-01532"
  - Campo data.estado = "pendiente_verificacion"
  - Campo message contiene el texto: "Pago del cliente registrado exitosamente"

### ✅ Caso 2:

- **Precondición:** La tabla de órdenes de venta no contiene una orden con el identificador VEN-99999.
- **Acción:** Ejecutar el endpoint POST /api/v1/pagos/cliente con ventaId VEN-99999 y un pago válido.
- **Resultado esperado:**
  - Código HTTP 404 Not Found
  - No se registra ningún pago
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No existe una orden de venta con el identificador indicado"

### ✅ Caso 3: 

- **Precondición:** Ejecución exitosa del endpoint.
- **Resultado esperado:** La respuesta JSON debe contener exactamente los campos:

  - "pagoId", "ventaId", "clienteId", "tipoPago", "medioPago", "numeroComprobante" y "estado" (texto)
  - "monto" y "valorTotalVenta" (número decimal)
  - "fechaPago" (fecha YYYY-MM-DD)
  - "fechaRegistro" (fecha y hora ISO 8601)
  - "message" (texto)
  - "success" (booleano)

### ❌ Caso 4: 

- **Precondición:** El asesor registra un pago con medioPago tarjeta (RN-41), o un abono sobre una orden con modalidad de pago total.
- **Acción:** Ejecutar el endpoint POST /api/v1/pagos/cliente con cada uno de esos datos inválidos.
- **Resultado esperado:**

  - Código HTTP 400 Bad Request
  - No se registra el pago
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "Solo se aceptan pagos en efectivo o transferencia" o "La orden de venta no permite pagos parciales", según el caso

### ❌ Caso 5: 

- **Precondición:** La base de datos no está disponible o ocurre un error en la consulta.
- **Acción:** Ejecutar el endpoint bajo condiciones simuladas de fallo de BD.
- **Resultado esperado:**
  - Código HTTP 503 Service Unavailable
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No fue posible registrar el pago del cliente"
