## 📖 Historia de Usuario

Dado que soy la administradora de One Click Caribe y debo autorizar los pagos a los proveedores de cada venta,
Para pagar a cada proveedor el valor neto correcto y solo cuando la agencia ya cobró al cliente,
Que el sistema me permita consultar el monto adeudado a cada proveedor de una orden de venta, ya descontada la comisión pactada.

## 🔁 Flujo Esperado

- La administradora obtiene desde la interfaz la orden de venta cuyos pagos a proveedores debe autorizar (proceso PRO-46).
- El sistema consume el endpoint /api/v1/pagos/proveedores/adeudado?ventaId=VEN-XXXXX de `pagos.api` con el método GET.
- La capa API valida el formato del parámetro y delega el caso de uso a `ConsultarMontoAdeudadoService`.
- El sistema consulta a `ventas.api` los segmentos de la orden con su proveedor y su precio de venta, y a `proveedores.api` la comisión pactada de cada proveedor.
- El backend consulta la base de datos `bd_pagos_tesoreria` filtrando por ventaId para conocer el estado de pago del cliente y los pagos a proveedores ya realizados.
- El dominio `pago_proveedores.domain` descuenta la comisión pactada del valor de hospedaje, traslados, tours y asistencia médica (proceso PRO-48, RN-48); en tiquetes aéreos el monto es el valor neto, sin descuento (RN-49).
- El dominio marca cada proveedor como habilitado para pago solo si el pago del cliente ya está confirmado, salvo que el proveedor haya autorizado pago diferido (RN-46).
- Se retorna, agrupado por proveedor, el monto adeudado con los campos:
- valorCobradoCliente / Valor cobrado al cliente por los servicios de ese proveedor
- comisionDescontada / Comisión que retiene la agencia
- montoAdeudado / Valor neto a transferir al proveedor
- habilitadoParaPago / Indica si el pago puede ejecutarse


## ✅ Criterios de Aceptación

### 1. 🔍 Estructura y lógica del servicio

- [ ] Se expone un endpoint GET con el parámetro ventaId.
- [ ] Se valida que la orden de venta exista; si no existe, se retorna código HTTP 404.
- [ ] El monto adeudado de hospedaje, traslados, tours y asistencia médica es el valor cobrado al cliente menos la comisión pactada (RN-48).
- [ ] El monto adeudado de tiquetes aéreos es el valor neto reportado, sin descuento de comisión (RN-49).
- [ ] Un proveedor solo queda habilitado para pago cuando el pago del cliente está verificado en su totalidad, salvo que haya autorizado pago diferido (RN-46).
- [ ] Los segmentos ya pagados a un proveedor no vuelven a sumarse al monto adeudado.

## 🧪 Requisitos de Pruebas

## 🔍 Casos de Prueba Funcional

### ✅ Caso 1: 

- **Precondición:** La orden VEN-01532 tiene el pago del cliente verificado en su totalidad y ningún pago a proveedores registrado.
- **Acción:** Ejecutar el endpoint GET /api/v1/pagos/proveedores/adeudado?ventaId=VEN-01532.
- **Resultado esperado:**

  - Código HTTP 200 OK
  - El proveedor de tiquete aéreo tiene comisionDescontada = 0 y montoAdeudado = 3960000
  - Los demás proveedores tienen montoAdeudado igual al valor cobrado menos la comisión pactada
  - Campo data.totalAdeudado = 10280000 y campo data.comisionTotal = 758400
  - Campo message contiene el texto: "Consulta de monto adeudado exitosa"

### ✅ Caso 2:

- **Precondición:** La orden VEN-01498 ya tiene registrados los pagos a todos sus proveedores.
- **Acción:** Ejecutar el endpoint con GET /api/v1/pagos/proveedores/adeudado?ventaId=VEN-01498.
- **Resultado esperado:**
  - Código HTTP 200 OK
  - Campo proveedores = []
  - Campo totalAdeudado = 0
  - Campo comisionTotal = 0
  - Campo message contiene el texto: "No existen montos pendientes de pago a proveedores para la orden indicada"

### ✅ Caso 3: 

- **Precondición:** Ejecución exitosa del endpoint.
- **Resultado esperado:** La respuesta JSON debe contener exactamente los campos:

  - "ventaId" y "estadoPagoOrden" (texto)
  - "proveedores" (lista), y en cada proveedor: "proveedorId" y "tipoServicio" (texto), "valorCobradoCliente", "comisionDescontada" y "montoAdeudado" (número decimal) y "habilitadoParaPago" (booleano)
  - "comisionTotal" y "totalAdeudado" (número decimal)
  - "message" (texto)
  - "success" (booleano)

### ❌ Caso 4: 

- **Precondición:** La administradora envía el parámetro ventaId con formato incorrecto (por ejemplo, "1532").
- **Acción:** Ejecutar el endpoint con GET /api/v1/pagos/proveedores/adeudado?ventaId=1532.
- **Resultado esperado:**

  - Código HTTP 400 Bad Request
  - No se realiza ninguna consulta de montos
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "Identificador de venta no válido. Debe tener el formato VEN-NNNNN"

### ❌ Caso 5: 

- **Precondición:** La base de datos no está disponible o ocurre un error en la consulta.
- **Acción:** Ejecutar el endpoint bajo condiciones simuladas de fallo de BD.
- **Resultado esperado:**
  - Código HTTP 503 Service Unavailable
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No fue posible consultar el monto adeudado a proveedores"
