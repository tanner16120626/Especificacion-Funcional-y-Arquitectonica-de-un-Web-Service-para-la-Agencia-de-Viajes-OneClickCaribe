## 📖 Historia de Usuario

Dado que soy asesor comercial de One Click Caribe y el cliente titular me indica hacia dónde quiere viajar, desde dónde sale y en qué fechas,
Para contar con la solicitud mínima que permite consultar disponibilidad y tarifa a los proveedores, incluso cuando el viaje combina varios destinos,
Que el sistema me permita registrar la solicitud de viaje con la ciudad y país de origen, uno o varios destinos y las fechas de salida y regreso.

## 🔁 Flujo Esperado

- El asesor comercial obtiene desde la interfaz el identificador del cliente titular, el origen, los destinos y las fechas del viaje.
- El sistema consume el endpoint /api/v1/solicitudes de `clientes.api` con el método POST.
- La capa API valida el formato del JSON y delega el caso de uso a `RegistrarSolicitudViajeService`.
- El backend consulta la base de datos `bd_clientes_solicitudes` filtrando por clienteId para confirmar que el cliente titular existe.
- El dominio `registro_parametros_viaje.domain` valida que la ciudad y el país de origen existan en el catálogo de ubicaciones (proceso PRO-08).
- El dominio valida la coherencia de las fechas: la salida debe ser anterior o igual al regreso (proceso PRO-07).
- El dominio admite uno o varios destinos asociados al mismo itinerario, en el orden en que se recorren (proceso PRO-06, RN-08).
- Se registra la solicitud con estado pendiente de alcance, ya que el tipo de servicio y la composición del grupo se definen después (RN-10), con los campos:
- clienteId / Identificador del cliente titular
- origen.ciudad, origen.pais / Ciudad y país de salida
- destinos[].ciudad, destinos[].pais, destinos[].orden / Destinos del itinerario y su orden
- fechaSalida / Fecha de salida (YYYY-MM-DD)
- fechaRegreso / Fecha de regreso (YYYY-MM-DD)


## ✅ Criterios de Aceptación

### 1. 🔍 Estructura y lógica del servicio

- [ ] Se expone un endpoint POST que recibe en el cuerpo JSON los campos clienteId, origen, destinos, fechaSalida y fechaRegreso.
- [ ] Se valida que el clienteId recibido tenga un registro en la tabla de clientes.
- [ ] Se valida que la ciudad y el país de origen existan en el catálogo de ubicaciones (PRO-08).
- [ ] Se valida que exista al menos un destino y se admiten varios destinos en una misma solicitud, cada uno con su orden en el itinerario (RN-08).
- [ ] Se valida que fechaSalida sea anterior o igual a fechaRegreso (PRO-07).
- [ ] La solicitud queda en estado pendiente_alcance, porque Cotizaciones no puede construir una propuesta sin el alcance del servicio definido (RN-10).

## 🧪 Requisitos de Pruebas

## 🔍 Casos de Prueba Funcional

### ✅ Caso 1: 

- **Precondición:** La tabla de clientes contiene el cliente titular CLI-00188 y el catálogo de ubicaciones contiene Bucaramanga (CO), Ciudad de México (MX) y Cancún (MX).
- **Acción:** Ejecutar el endpoint POST /api/v1/solicitudes con origen Bucaramanga, destinos Ciudad de México (orden 1) y Cancún (orden 2), salida 2026-12-10 y regreso 2026-12-20.
- **Resultado esperado:**

  - Código HTTP 201 Created
  - Campo success = true
  - Campo data.solicitudId contiene el identificador asignado a la solicitud
  - Campo data.destinos contiene los dos destinos en el orden enviado
  - Campo data.estado = "pendiente_alcance"
  - Campo message contiene el texto: "Solicitud de viaje registrada exitosamente"

### ✅ Caso 2:

- **Precondición:** La tabla de clientes no contiene un cliente titular con el identificador CLI-99999.
- **Acción:** Ejecutar el endpoint POST /api/v1/solicitudes con clienteId CLI-99999 y un itinerario válido.
- **Resultado esperado:**
  - Código HTTP 404 Not Found
  - No se registra la solicitud
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No existe un cliente titular con el identificador indicado"

### ✅ Caso 3: 

- **Precondición:** Ejecución exitosa del endpoint.
- **Resultado esperado:** La respuesta JSON debe contener exactamente los campos:

  - "solicitudId" (texto)
  - "clienteId" (texto)
  - "origen" (objeto con "ciudad" y "pais" de tipo texto)
  - "destinos" (lista de objetos con "orden" de tipo número entero, "ciudad" y "pais" de tipo texto)
  - "fechaSalida" y "fechaRegreso" (fecha YYYY-MM-DD)
  - "estado" (texto)
  - "fechaRegistro" (fecha y hora ISO 8601)
  - "message" (texto)
  - "success" (booleano)

### ❌ Caso 4: 

- **Precondición:** El asesor envía una fechaRegreso anterior a la fechaSalida (salida 2026-12-20 y regreso 2026-12-10), o un origen que no existe en el catálogo de ubicaciones.
- **Acción:** Ejecutar el endpoint POST /api/v1/solicitudes con cada uno de esos datos inválidos.
- **Resultado esperado:**

  - Código HTTP 400 Bad Request
  - No se registra la solicitud
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "La fecha de salida debe ser anterior o igual a la fecha de regreso" o "La ubicación de origen no existe en el catálogo", según el caso

### ❌ Caso 5: 

- **Precondición:** La base de datos no está disponible o ocurre un error en la consulta.
- **Acción:** Ejecutar el endpoint bajo condiciones simuladas de fallo de BD.
- **Resultado esperado:**
  - Código HTTP 503 Service Unavailable
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No fue posible registrar la solicitud de viaje"
