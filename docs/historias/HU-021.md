## 📖 Historia de Usuario

Dado que soy asesor comercial de One Click Caribe y el cliente aceptó la cotización dentro de su día de vigencia,
Para formalizar la venta y pasar de la negociación a la operación con un código propio, trazable hasta la cotización de origen,
Que el sistema me permita generar la orden de venta desde la cotización aceptada, con las condiciones de pago acordadas y el detalle exacto de los servicios vendidos.

## 🔁 Flujo Esperado

- El asesor comercial obtiene desde la interfaz la cotización aceptada y las condiciones de pago acordadas con el cliente: pago total o parcial, y fecha límite del saldo cuando es parcial (procesos PRO-31 y PRO-33).
- El sistema consume el endpoint /api/v1/ventas de `ventas.api` con el método POST.
- La capa API valida el formato del JSON y delega el caso de uso a `GenerarOrdenVentaService`.
- El sistema consulta a `cotizaciones.api` (GET /cotizaciones/{id}) el detalle de la cotización y valida que esté aceptada y vigente (RN-31).
- El dominio `formalizacion_orden_venta.domain` genera un código de venta nuevo, distinto del código de la cotización, y registra el vínculo entre ambos (proceso PRO-32, RN-32, RN-35).
- El dominio copia en la orden los proveedores y precios exactos de la cotización aceptada y bloquea cualquier modificación posterior de esos valores (proceso PRO-34, RN-34).
- Si el pago es parcial, el dominio registra la fecha límite máxima del saldo restante (RN-33).
- Se registra la orden de venta en estado pendiente de pago, porque el precio solo queda garantizado con el pago del cliente el mismo día (RN-27), con los campos:
- ventaId / Código único de la orden de venta
- cotizacionId / Cotización de origen vinculada
- segmentos / Servicios, proveedores y precios copiados de la cotización
- condicionesPago.modalidad / total o parcial
- condicionesPago.fechaLimiteSaldo / Fecha límite del saldo cuando el pago es parcial
- valorTotal / Valor total de la venta


## ✅ Criterios de Aceptación

### 1. 🔍 Estructura y lógica del servicio

- [ ] Se expone un endpoint POST que recibe en el cuerpo JSON el cotizacionId y las condiciones de pago acordadas.
- [ ] Se valida que la cotización exista, esté aceptada y siga vigente; solo una cotización vigente y aceptada puede convertirse en orden de venta (RN-31).
- [ ] Se valida que la cotización no tenga ya una orden de venta generada; si la tiene, se retorna la orden existente con código HTTP 409.
- [ ] El ventaId generado es único y distinto del cotizacionId, y la orden conserva en todo momento el vínculo con su cotización de origen (RN-32, RN-35).
- [ ] Los segmentos, proveedores y precios de la orden son exactamente los de la cotización aceptada y no pueden modificarse después (RN-34).
- [ ] Si la modalidad es parcial, fechaLimiteSaldo es obligatoria y debe ser anterior a la fecha de salida del viaje (RN-33).

## 🧪 Requisitos de Pruebas

## 🔍 Casos de Prueba Funcional

### ✅ Caso 1: 

- **Precondición:** La cotización COT-07421 está aceptada, vigente hasta las 23:59:59 del día y sin orden de venta generada.
- **Acción:** Ejecutar el endpoint POST /api/v1/ventas con cotizacionId COT-07421, modalidad parcial y fechaLimiteSaldo 2026-11-20.
- **Resultado esperado:**

  - Código HTTP 201 Created
  - Campo data.ventaId contiene un código distinto de COT-07421 y campo data.cotizacionId = "COT-07421"
  - Los segmentos y precios de la orden son iguales a los de la cotización, y data.valorTotal = 11038400
  - Campo data.estado = "pendiente_pago"
  - Campo message contiene el texto: "Orden de venta generada exitosamente"

### ✅ Caso 2:

- **Precondición:** La tabla de cotizaciones no contiene una cotización con el identificador COT-99999.
- **Acción:** Ejecutar el endpoint POST /api/v1/ventas con cotizacionId COT-99999.
- **Resultado esperado:**
  - Código HTTP 404 Not Found
  - No se genera ninguna orden de venta
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No existe una cotización con el identificador indicado"

### ✅ Caso 3: 

- **Precondición:** Ejecución exitosa del endpoint.
- **Resultado esperado:** La respuesta JSON debe contener exactamente los campos:

  - "ventaId", "cotizacionId" y "clienteId" (texto)
  - "segmentos" (lista), y en cada segmento: "orden" (número entero), "tipoServicio" y "proveedorId" (texto) y "precioVenta" (número decimal)
  - "condicionesPago" (objeto con "modalidad" de tipo texto y "fechaLimiteSaldo" de tipo fecha YYYY-MM-DD, o null si el pago es total)
  - "valorTotal" (número decimal)
  - "moneda" y "estado" (texto)
  - "fechaCreacion" (fecha y hora ISO 8601)
  - "message" (texto)
  - "success" (booleano)

### ❌ Caso 4: 

- **Precondición:** El asesor intenta generar la orden desde la cotización COT-07415, que está vencida (RN-31), o envía modalidad parcial sin fechaLimiteSaldo (RN-33).
- **Acción:** Ejecutar el endpoint POST /api/v1/ventas con cada uno de esos datos inválidos.
- **Resultado esperado:**

  - Código HTTP 400 Bad Request
  - No se genera la orden de venta
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "Solo una cotización vigente y aceptada puede convertirse en orden de venta" o "La fecha límite del saldo es obligatoria cuando el pago es parcial", según el caso

### ❌ Caso 5: 

- **Precondición:** La base de datos no está disponible o ocurre un error en la consulta.
- **Acción:** Ejecutar el endpoint bajo condiciones simuladas de fallo de BD.
- **Resultado esperado:**
  - Código HTTP 503 Service Unavailable
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No fue posible generar la orden de venta"
