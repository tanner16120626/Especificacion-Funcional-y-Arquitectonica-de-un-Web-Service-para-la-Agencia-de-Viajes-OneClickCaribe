## 📖 Historia de Usuario

Dado que soy la administradora de One Click Caribe y el asesor comercial registró un pago del cliente con su comprobante,
Para dar por recaudado únicamente el dinero que efectivamente ingresó al banco, separando la verificación financiera de la operación comercial,
Que el sistema me permita confirmar o rechazar el pago contra el ingreso real en la cuenta y recalcular el saldo pendiente de la orden de venta.

## 🔁 Flujo Esperado

- La administradora obtiene desde la interfaz el pago pendiente de verificación y el resultado de su revisión en la cuenta bancaria de la agencia (proceso PRO-42).
- El sistema consume el endpoint /api/v1/pagos/cliente/{pagoId}/verificacion de `pagos.api` con el método PUT.
- La capa API valida el formato del JSON y delega el caso de uso a `VerificarPagoClienteService`.
- El backend consulta la base de datos `bd_pagos_tesoreria` filtrando por pagoId para confirmar que el pago existe y está en estado pendiente de verificación.
- El dominio `recaudo_verificacion_pago.domain` marca el pago como verificado solo si corresponde a un ingreso real en la cuenta, porque el comprobante no es prueba suficiente (RN-42).
- El dominio obtiene el valor total de la orden, resta los pagos verificados y calcula el saldo pendiente (proceso PRO-44).
- La orden solo se considera pagada en su totalidad cuando el saldo pendiente verificado es cero (RN-45).
- Se registra la verificación con los campos:
- resultado / verificado o rechazado
- observacion / Detalle de la revisión, obligatorio cuando se rechaza
- fechaIngreso / Fecha en que el dinero ingresó a la cuenta
- totalVerificado / Suma de los pagos verificados de la orden
- saldoPendiente / Valor que falta por pagar
- estadoPagoOrden / sin_pago, pago_parcial o pagada


## ✅ Criterios de Aceptación

### 1. 🔍 Estructura y lógica del servicio

- [ ] Se expone un endpoint PUT con el parámetro pagoId en la ruta y el resultado de la verificación en el cuerpo JSON.
- [ ] Se valida que el pago exista y esté en estado pendiente_verificacion; un pago ya verificado o rechazado no se vuelve a verificar.
- [ ] Un pago solo pasa a verificado cuando la administradora confirma el ingreso real en la cuenta; el comprobante por sí solo no lo confirma (RN-42).
- [ ] Se valida que observacion esté informada cuando el resultado es rechazado; un pago rechazado no suma al total verificado.
- [ ] El saldo pendiente se calcula como el valor total de la orden menos la suma de los pagos verificados (PRO-44).
- [ ] La orden solo cambia a estado de pago pagada cuando el saldo pendiente verificado es cero (RN-45).

## 🧪 Requisitos de Pruebas

## 🔍 Casos de Prueba Funcional

### ✅ Caso 1: 

- **Precondición:** El pago PAG-02210 por 5000000 está en estado pendiente_verificacion, asociado a la orden VEN-01532 de 11038400, y el dinero ya ingresó a la cuenta de la agencia.
- **Acción:** Ejecutar el endpoint PUT /api/v1/pagos/cliente/PAG-02210/verificacion con resultado verificado y fechaIngreso 2026-10-22.
- **Resultado esperado:**

  - Código HTTP 200 OK
  - Campo data.resultado = "verificado"
  - Campo data.totalVerificado = 5000000 y campo data.saldoPendiente = 6038400
  - Campo data.estadoPagoOrden = "pago_parcial"
  - Campo message contiene el texto: "Verificación del pago registrada exitosamente"

### ✅ Caso 2:

- **Precondición:** La tabla de pagos no contiene un pago con el identificador PAG-99999.
- **Acción:** Ejecutar el endpoint PUT /api/v1/pagos/cliente/PAG-99999/verificacion con resultado verificado.
- **Resultado esperado:**
  - Código HTTP 404 Not Found
  - No se modifica ningún pago ni saldo
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No existe un pago con el identificador indicado"

### ✅ Caso 3: 

- **Precondición:** Ejecución exitosa del endpoint.
- **Resultado esperado:** La respuesta JSON debe contener exactamente los campos:

  - "pagoId", "ventaId", "resultado" y "estadoPagoOrden" (texto)
  - "montoVerificado", "valorTotalVenta", "totalVerificado" y "saldoPendiente" (número decimal)
  - "fechaIngreso" (fecha YYYY-MM-DD)
  - "fechaVerificacion" (fecha y hora ISO 8601)
  - "message" (texto)
  - "success" (booleano)

### ❌ Caso 4: 

- **Precondición:** La administradora intenta verificar el pago PAG-02210, que ya está verificado, o registra un rechazo sin observación.
- **Acción:** Ejecutar el endpoint PUT /api/v1/pagos/cliente/PAG-02210/verificacion con cada uno de esos datos inválidos.
- **Resultado esperado:**

  - Código HTTP 400 Bad Request
  - No se modifica el pago ni el saldo de la orden
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "El pago ya fue verificado o rechazado" o "La observación es obligatoria cuando se rechaza un pago", según el caso

### ❌ Caso 5: 

- **Precondición:** La base de datos no está disponible o ocurre un error en la consulta.
- **Acción:** Ejecutar el endpoint bajo condiciones simuladas de fallo de BD.
- **Resultado esperado:**
  - Código HTTP 503 Service Unavailable
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No fue posible registrar la verificación del pago"
