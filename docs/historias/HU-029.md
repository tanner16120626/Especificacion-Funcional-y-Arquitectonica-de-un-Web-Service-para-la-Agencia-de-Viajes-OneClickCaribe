## 📖 Historia de Usuario

Dado que soy la administradora de One Click Caribe y el proveedor ya está habilitado para pago porque la agencia cobró al cliente,
Para cerrar la obligación con el proveedor, conocer el costo real de la venta y permitir que la reserva se confirme,
Que el sistema me permita registrar el pago realizado a un proveedor en su plataforma, asociado a la orden de venta y a los segmentos que cubre.

## 🔁 Flujo Esperado

- La administradora obtiene desde la interfaz la orden de venta, el proveedor, los segmentos pagados, el monto transferido y la referencia del pago hecho en la plataforma del proveedor (proceso PRO-47).
- El sistema consume el endpoint /api/v1/pagos/proveedores de `pagos.api` con el método POST.
- La capa API valida el formato del JSON y delega el caso de uso a `RegistrarPagoProveedorService`.
- El backend consulta la base de datos `bd_pagos_tesoreria` filtrando por ventaId y proveedorId para obtener el monto adeudado y confirmar que los segmentos no estén pagados.
- El dominio `pago_proveedores.domain` ejecuta `PagoProveedor.puedeEjecutarse()`: el pago solo procede si el pago del cliente está confirmado o si el proveedor autorizó pago diferido (RN-46).
- El dominio valida que el monto corresponda al valor neto adeudado, con la comisión ya descontada en hospedaje, traslados, tours y asistencia médica (RN-48), y sin descuento en tiquetes aéreos (RN-49).
- Se asocia el egreso a la orden y al proveedor, se marcan los segmentos como pagados y se notifica a `reservas.api` (POST /reservas/habilitar-pago) que la reserva de esos segmentos ya puede confirmarse.
- El pago queda pendiente de vincular el voucher que entregue el proveedor (RN-50), con los campos:
- ventaId / Orden de venta
- proveedorId / Proveedor pagado
- segmentos / Segmentos de la orden que cubre el pago
- montoPagado / Valor neto transferido
- referenciaPago / Referencia del pago en la plataforma del proveedor
- fechaPago / Fecha del pago


## ✅ Criterios de Aceptación

### 1. 🔍 Estructura y lógica del servicio

- [ ] Se expone un endpoint POST que recibe en el cuerpo JSON los campos ventaId, proveedorId, segmentos, montoPagado, referenciaPago y fechaPago.
- [ ] Se valida que la orden exista y que el proveedor tenga segmentos en ella.
- [ ] Se valida que el pago pueda ejecutarse: pago del cliente confirmado o pago diferido autorizado por el proveedor (RN-46).
- [ ] Se valida que montoPagado sea igual al monto adeudado de esos segmentos: valor cobrado menos comisión en servicios con comisión (RN-48) y valor neto en tiquetes aéreos (RN-49).
- [ ] Se valida que los segmentos no tengan un pago previo; un segmento ya pagado no se vuelve a pagar.
- [ ] Al registrarse el pago, los segmentos quedan marcados como pagados, se habilita su reserva en Reservas y Confirmaciones, y el pago queda pendiente_voucher hasta vincular el voucher del proveedor (RN-50).

## 🧪 Requisitos de Pruebas

## 🔍 Casos de Prueba Funcional

### ✅ Caso 1: 

- **Precondición:** La orden VEN-01532 tiene el pago del cliente verificado en su totalidad y el proveedor PRV-0021 tiene los segmentos 3 y 4 sin pagar, con un monto adeudado de 3320000.
- **Acción:** Ejecutar el endpoint POST /api/v1/pagos/proveedores con ventaId VEN-01532, proveedorId PRV-0021, segmentos 3 y 4, montoPagado 3320000 y referenciaPago PT-AGC-559120.
- **Resultado esperado:**

  - Código HTTP 201 Created
  - Campo data.comisionRetenida = 398400
  - Campo data.reservaHabilitada = true
  - Campo data.estado = "pendiente_voucher"
  - Campo message contiene el texto: "Pago a proveedor registrado exitosamente"

### ✅ Caso 2:

- **Precondición:** El proveedor PRV-0050 no tiene segmentos en la orden VEN-01532.
- **Acción:** Ejecutar el endpoint POST /api/v1/pagos/proveedores con ventaId VEN-01532 y proveedorId PRV-0050.
- **Resultado esperado:**
  - Código HTTP 404 Not Found
  - No se registra ningún pago a proveedor
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No existe la orden de venta o el proveedor no participa en ella"

### ✅ Caso 3: 

- **Precondición:** Ejecución exitosa del endpoint.
- **Resultado esperado:** La respuesta JSON debe contener exactamente los campos:

  - "pagoProveedorId", "ventaId", "proveedorId", "referenciaPago" y "estado" (texto)
  - "segmentos" (lista de números enteros)
  - "valorCobradoCliente", "comisionRetenida" y "montoPagado" (número decimal)
  - "fechaPago" (fecha YYYY-MM-DD)
  - "reservaHabilitada" (booleano)
  - "fechaRegistro" (fecha y hora ISO 8601)
  - "message" (texto)
  - "success" (booleano)

### ❌ Caso 4: 

- **Precondición:** La administradora registra un montoPagado de 3718400, sin descontar la comisión (RN-48), o intenta pagar al proveedor de la orden VEN-01540, cuyo cliente aún no completa su pago y que no tiene pago diferido autorizado (RN-46).
- **Acción:** Ejecutar el endpoint POST /api/v1/pagos/proveedores con cada uno de esos datos inválidos.
- **Resultado esperado:**

  - Código HTTP 400 Bad Request
  - No se registra el pago ni se habilita la reserva
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "El monto no corresponde al valor neto adeudado al proveedor" o "No puede pagarse al proveedor antes de confirmar el pago del cliente", según el caso

### ❌ Caso 5: 

- **Precondición:** La base de datos no está disponible o ocurre un error en la consulta.
- **Acción:** Ejecutar el endpoint bajo condiciones simuladas de fallo de BD.
- **Resultado esperado:**
  - Código HTTP 503 Service Unavailable
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No fue posible registrar el pago al proveedor"
