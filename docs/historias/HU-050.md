## 📖 Historia de Usuario

Dado que soy asesor comercial de One Click Caribe y un cliente con un viaje ya vendido me escribe por WhatsApp, me llama o viene a la oficina con una duda,
Para que ninguna inquietud del cliente se pierda entre canales y quede vinculada al historial de su orden de venta,
Que el sistema me permita registrar la consulta posventa asociada a la orden, con el canal de atención y el detalle de la venta para responder informadamente.

## 🔁 Flujo Esperado

- El asesor comercial obtiene desde la interfaz la orden de venta, el canal por el que llegó la consulta, su categoría y la descripción de la inquietud (proceso PRO-81).
- El sistema consume el endpoint /api/v1/posventa/consultas de `posventa.api` con el método POST.
- La capa API valida el formato del JSON y delega el caso de uso a `RegistrarConsultaPosventaService`.
- El dominio `acompanamiento_asesoria_posventa.domain` ejecuta `ConsultaPosventa.generaCambio()`: una consulta no puede generar cambios en la orden ni en la reserva; si implica un ajuste real, debe derivarse a Gestión de Cambios Posventa (RN-81).
- El sistema consulta a `ventas.api` (GET /ventas/{id}/detalle) el detalle de la venta y de la reserva asociada, y vincula la consulta al historial de esa orden (proceso PRO-82, RN-83).
- El dominio identifica y registra el canal por el que llegó la consulta: whatsapp, llamada o presencial (proceso PRO-84, RN-82).
- Se registra la consulta en estado abierta, sin vigencia limitada, en la base de datos `bd_posventa` (RN-85), con los campos:
- ventaId / Orden de venta asociada
- canal / whatsapp, llamada o presencial
- categoria / documentacion, itinerario o condiciones_servicio
- descripcion / Detalle de la inquietud del cliente
- resumenOrden / Estado de la orden, servicios y fecha de salida para atender la consulta


## ✅ Criterios de Aceptación

### 1. 🔍 Estructura y lógica del servicio

- [ ] Se expone un endpoint POST que recibe en el cuerpo JSON los campos ventaId, canal, categoria y descripcion.
- [ ] Se valida que la orden de venta exista; toda consulta queda asociada a una orden específica (RN-83).
- [ ] Se valida que canal sea whatsapp, llamada o presencial (RN-82).
- [ ] Se valida que la consulta no implique un cambio transaccional; las solicitudes de cambio de fecha, equipaje o actividades se rechazan aquí y se derivan a Gestión de Cambios Posventa (RN-81).
- [ ] La respuesta incluye el resumen de la orden y de su reserva para que el asesor responda con información de la venta (PRO-82).
- [ ] La consulta queda en estado abierta y se conserva en el historial sin fecha de vencimiento (RN-85).

## 🧪 Requisitos de Pruebas

## 🔍 Casos de Prueba Funcional

### ✅ Caso 1: 

- **Precondición:** La orden de venta VEN-01532 existe y está pagada.
- **Acción:** Ejecutar el endpoint POST /api/v1/posventa/consultas con ventaId VEN-01532, canal whatsapp, categoria documentacion y la descripción de la inquietud.
- **Resultado esperado:**

  - Código HTTP 201 Created
  - Campo data.consultaId contiene el identificador asignado a la consulta
  - Campo data.resumenOrden contiene el estado de la orden y de su reserva
  - Campo data.estado = "abierta"
  - Campo message contiene el texto: "Consulta posventa registrada exitosamente"

### ✅ Caso 2:

- **Precondición:** La tabla de órdenes de venta no contiene una orden con el identificador VEN-99999.
- **Acción:** Ejecutar el endpoint POST /api/v1/posventa/consultas con ventaId VEN-99999 y una consulta válida.
- **Resultado esperado:**
  - Código HTTP 404 Not Found
  - No se registra ninguna consulta
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No existe una orden de venta con el identificador indicado"

### ✅ Caso 3: 

- **Precondición:** Ejecución exitosa del endpoint.
- **Resultado esperado:** La respuesta JSON debe contener exactamente los campos:

  - "consultaId", "ventaId", "clienteId", "canal", "categoria", "descripcion" y "estado" (texto)
  - "resumenOrden" (objeto con "estadoOrden" y "estadoReserva" de tipo texto, "totalServicios" de tipo número entero y "fechaSalida" de tipo fecha YYYY-MM-DD)
  - "fechaRegistro" (fecha y hora ISO 8601)
  - "message" (texto)
  - "success" (booleano)

### ❌ Caso 4: 

- **Precondición:** El asesor intenta registrar como consulta una solicitud de cambio de fecha del viaje (RN-81), o envía el canal "correo", que no es un canal de atención posventa (RN-82).
- **Acción:** Ejecutar el endpoint POST /api/v1/posventa/consultas con cada uno de esos datos inválidos.
- **Resultado esperado:**

  - Código HTTP 400 Bad Request
  - No se registra la consulta ni se modifica la orden
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "Las solicitudes de cambio deben gestionarse en Gestión de Cambios Posventa" o "Canal de atención no válido. Debe ser whatsapp, llamada o presencial", según el caso

### ❌ Caso 5: 

- **Precondición:** La base de datos no está disponible o ocurre un error en la consulta.
- **Acción:** Ejecutar el endpoint bajo condiciones simuladas de fallo de BD.
- **Resultado esperado:**
  - Código HTTP 503 Service Unavailable
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No fue posible registrar la consulta posventa"
