## 📖 Historia de Usuario

Dado que soy asesor comercial de One Click Caribe y el proveedor ya respondió la solicitud de reserva de un segmento,
Para tener evidencia verificable de que cada servicio quedó reservado tal como se vendió, y detectar a tiempo cualquier error,
Que el sistema me permita registrar el código de confirmación o localizador del proveedor y verificar que coincida con los datos de la orden de venta.

## 🔁 Flujo Esperado

- El asesor comercial obtiene desde la interfaz la reserva solicitada y la respuesta del proveedor: localizador, pasajeros, fechas y servicio confirmados (proceso PRO-62).
- El sistema consume el endpoint /api/v1/reservas/{reservaId}/confirmacion de `reservas.api` con el método PUT.
- La capa API valida el formato del JSON y delega el caso de uso a `RegistrarConfirmacionReservaService`.
- El backend consulta la base de datos `bd_reservas` filtrando por reservaId para confirmar que la reserva existe y está en estado solicitada.
- El dominio `emision_confirmacion_reserva.domain` asocia el localizador exclusivamente a ese segmento, aunque otros segmentos de la orden sean del mismo proveedor (RN-62).
- El sistema consulta a `ventas.api` el detalle vendido del segmento y a `clientes.api` los pasajeros de la orden, y el dominio contrasta pasajeros, fechas y servicio confirmados contra lo vendido (proceso PRO-63).
- Si todo coincide, el segmento queda confirmado; si hay diferencias, queda con discrepancia y se reporta de inmediato (RN-63), con los campos:
- localizador / Código de confirmación entregado por el proveedor
- pasajerosConfirmados / Pasajeros que figuran en la confirmación
- fechaInicio y fechaFin / Fechas confirmadas del servicio
- verificacion / Resultado del contraste contra la orden de venta
- discrepancias / Diferencias encontradas, cuando existen


## ✅ Criterios de Aceptación

### 1. 🔍 Estructura y lógica del servicio

- [ ] Se expone un endpoint PUT con el parámetro reservaId en la ruta y los datos de la confirmación del proveedor en el cuerpo JSON.
- [ ] Se valida que la reserva exista y esté en estado solicitada; si no existe, se retorna código HTTP 404.
- [ ] Se valida que el localizador esté informado y que no esté asociado a otro segmento; cada segmento tiene su propio código de confirmación (RN-62).
- [ ] Se contrastan los pasajeros, las fechas y el servicio confirmados contra los datos de la orden de venta (PRO-63).
- [ ] Si todo coincide, el segmento cambia a estado confirmada; si existe cualquier diferencia, cambia a con_discrepancia y la respuesta detalla cada diferencia para reportarla al proveedor (RN-63).

## 🧪 Requisitos de Pruebas

## 🔍 Casos de Prueba Funcional

### ✅ Caso 1: 

- **Precondición:** La reserva RES-02904 (hospedaje en Cancún, segmento 3 de la orden VEN-01532) está en estado solicitada, vendida para María Fernanda Rojas Díaz y Andrés Felipe Gómez Pinto del 2026-12-15 al 2026-12-20.
- **Acción:** Ejecutar el endpoint PUT /api/v1/reservas/RES-02904/confirmacion con localizador PTX-7781QK, los dos pasajeros y las fechas 2026-12-15 a 2026-12-20.
- **Resultado esperado:**

  - Código HTTP 200 OK
  - Campo data.verificacion contiene coincidenPasajeros, coincidenFechas y coincideServicio = true
  - Campo data.discrepancias = []
  - Campo data.estado = "confirmada"
  - Campo message contiene el texto: "Confirmación de reserva registrada y verificada exitosamente"

### ✅ Caso 2:

- **Precondición:** La reserva RES-02904 está en estado solicitada y el proveedor confirmó la salida el 2026-12-19, un día antes de la fecha vendida.
- **Acción:** Ejecutar el endpoint con PUT /api/v1/reservas/RES-02904/confirmacion con localizador PTX-7781QK y fechaFin 2026-12-19.
- **Resultado esperado:**
  - Código HTTP 200 OK
  - Campo coincidenFechas = false
  - Campo discrepancias contiene la diferencia en fechaFin
  - Campo estado = "con_discrepancia"
  - Campo message contiene el texto: "La confirmación del proveedor no coincide con la orden de venta. Repórtela al proveedor"

### ✅ Caso 3: 

- **Precondición:** Ejecución exitosa del endpoint.
- **Resultado esperado:** La respuesta JSON debe contener exactamente los campos:

  - "reservaId", "ventaId", "proveedorId", "localizador" y "estado" (texto)
  - "orden" (número entero)
  - "pasajerosConfirmados" y "discrepancias" (lista de texto)
  - "fechaInicio" y "fechaFin" (fecha YYYY-MM-DD)
  - "verificacion" (objeto con "coincidenPasajeros", "coincidenFechas" y "coincideServicio" de tipo booleano)
  - "fechaConfirmacion" (fecha y hora ISO 8601)
  - "message" (texto)
  - "success" (booleano)

### ❌ Caso 4: 

- **Precondición:** El asesor envía la confirmación sin localizador, o con fechaInicio en formato incorrecto (por ejemplo, "15-12-2026").
- **Acción:** Ejecutar el endpoint PUT /api/v1/reservas/RES-02904/confirmacion con cada uno de esos datos inválidos.
- **Resultado esperado:**

  - Código HTTP 400 Bad Request
  - No se registra la confirmación y la reserva sigue en estado solicitada
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "El localizador del proveedor es obligatorio" o "Formato de fecha no válido. Debe ser YYYY-MM-DD", según el caso

### ❌ Caso 5: 

- **Precondición:** La base de datos no está disponible o ocurre un error en la consulta.
- **Acción:** Ejecutar el endpoint bajo condiciones simuladas de fallo de BD.
- **Resultado esperado:**
  - Código HTTP 503 Service Unavailable
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No fue posible registrar la confirmación de la reserva"
