## 📖 Historia de Usuario

Dado que soy asesor comercial de One Click Caribe y la cotización ya tiene calculado el precio de venta de cada segmento,
Para entregar al cliente una propuesta clara con la que pueda decidir, sabiendo cuánto le corresponde pagar a cada pasajero del grupo,
Que el sistema me permita consolidar la cotización final con el valor individual de cada pasajero y el total del viaje.

## 🔁 Flujo Esperado

- El asesor comercial obtiene desde la interfaz la cotización calculada y los pasajeros que viajan, asociados previamente al cliente titular (proceso PRO-25).
- El sistema consume el endpoint /api/v1/cotizaciones/{cotizacionId}/consolidacion de `cotizaciones.api` con el método POST.
- La capa API valida el formato del JSON y delega el caso de uso a `ConsolidarCotizacionService`.
- El backend consulta la base de datos `bd_cotizaciones` filtrando por cotizacionId para confirmar que la cotización existe y está en estado calculada.
- El sistema consulta a `clientes.api` (GET /clientes/{id}/pasajeros) la edad de cada pasajero para clasificarlo como adulto o menor.
- El dominio `construccion_cotizacion.domain` valida que los pasajeros coincidan con la composición del grupo registrada en la solicitud.
- El dominio calcula el valor de cada pasajero de forma individual, sin tarifas por grupo (RN-06), y agrupa todos los segmentos ya procesados en el documento final.
- Se registra la cotización consolidada, lista para enviarse al cliente, con los campos:
- pasajeros[].pasajeroId / Identificador del pasajero
- pasajeros[].nombre / Nombre del pasajero
- pasajeros[].tipoPasajero / adulto o menor
- pasajeros[].valorTotal / Valor total del viaje para ese pasajero
- totalCotizacion / Valor total de la cotización


## ✅ Criterios de Aceptación

### 1. 🔍 Estructura y lógica del servicio

- [ ] Se expone un endpoint POST con el parámetro cotizacionId en la ruta y la lista de pasajeroIds en el cuerpo JSON.
- [ ] Se valida que la cotización exista y esté en estado calculada; una cotización sin precio de venta calculado no se consolida.
- [ ] Se valida que los pasajeros pertenezcan al cliente titular de la solicitud y que su número de adultos y menores coincida con la composición del grupo registrada.
- [ ] El valor de cada pasajero se calcula de forma individual según su tipo, adulto o menor; no se aplican tarifas por grupo (RN-06).
- [ ] La suma de los valores individuales de los pasajeros es igual a totalCotizacion.
- [ ] La cotización cambia a estado consolidada, lista para enviarse al cliente.

## 🧪 Requisitos de Pruebas

## 🔍 Casos de Prueba Funcional

### ✅ Caso 1: 

- **Precondición:** La cotización COT-07421 está en estado calculada para 2 adultos, y los pasajeros PAS-00412 y PAS-00413 son adultos asociados al cliente titular CLI-00188.
- **Acción:** Ejecutar el endpoint POST /api/v1/cotizaciones/COT-07421/consolidacion con los pasajeros PAS-00412 y PAS-00413.
- **Resultado esperado:**

  - Código HTTP 200 OK
  - Cada pasajero tiene tipoPasajero = "adulto" y valorTotal = 5519200
  - Campo data.totalCotizacion = 11038400, igual a la suma de los valores individuales
  - Campo data.estado = "consolidada"
  - Campo message contiene el texto: "Cotización consolidada exitosamente"

### ✅ Caso 2:

- **Precondición:** La tabla de cotizaciones no contiene una cotización con el identificador COT-99999.
- **Acción:** Ejecutar el endpoint POST /api/v1/cotizaciones/COT-99999/consolidacion con pasajeros válidos.
- **Resultado esperado:**
  - Código HTTP 404 Not Found
  - No se consolida ninguna cotización
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No existe una cotización con el identificador indicado"

### ✅ Caso 3: 

- **Precondición:** Ejecución exitosa del endpoint.
- **Resultado esperado:** La respuesta JSON debe contener exactamente los campos:

  - "cotizacionId" y "clienteId" (texto)
  - "segmentosIncluidos" (número entero)
  - "pasajeros" (lista), y en cada pasajero: "pasajeroId", "nombre" y "tipoPasajero" (texto) y "valorTotal" (número decimal)
  - "totalCotizacion" (número decimal)
  - "moneda" y "estado" (texto)
  - "fechaConsolidacion" (fecha y hora ISO 8601)
  - "message" (texto)
  - "success" (booleano)

### ❌ Caso 4: 

- **Precondición:** La cotización COT-07421 todavía está en estado en_construccion, sin precio de venta calculado, o el asesor envía tres pasajeros cuando la composición registrada es de 2 adultos.
- **Acción:** Ejecutar el endpoint POST /api/v1/cotizaciones/COT-07421/consolidacion con cada uno de esos datos inválidos.
- **Resultado esperado:**

  - Código HTTP 400 Bad Request
  - No se consolida la cotización
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "La cotización debe tener el precio de venta calculado" o "Los pasajeros no coinciden con la composición del grupo", según el caso

### ❌ Caso 5: 

- **Precondición:** La base de datos no está disponible o ocurre un error en la consulta.
- **Acción:** Ejecutar el endpoint bajo condiciones simuladas de fallo de BD.
- **Resultado esperado:**
  - Código HTTP 503 Service Unavailable
  - Campo success = false y campo data = null
  - Campo message contiene el texto: "No fue posible consolidar la cotización"
